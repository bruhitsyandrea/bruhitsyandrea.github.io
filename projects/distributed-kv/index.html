CAUSAL CONSISTENCY

Which update
happened first?

In a distributed system, there is no single global clock that can reliably order every event. Vector clocks allow replicas to track causal relationships between updates using logical counters.

NODE A

Update X

A: 1 B: 0
↓
PUT status = "online"
↓
A: 2 B: 0
≠ CONCURRENT
NODE B

Update Y

A: 0 B: 1
↓
PUT status = "busy"
↓
A: 0 B: 2
↘     gossip / compare     ↙
CAUSAL METADATA
A: 2 B: 2

Comparing vector clocks reveals whether one update causally follows another or whether the updates occurred concurrently.

→

Happened Before

[1, 0] → [2, 0]

If every component is less than or equal to another vector, with at least one smaller component, the first event happened before the second.

∥

Concurrent

[2, 0] ∥ [0, 2]

If neither vector dominates the other, the system cannot establish a causal ordering between the two updates.

max

Merge

max([2,0], [0,2]) = [2,2]

When replicas exchange metadata, their logical clocks can be merged by taking the maximum counter for each node.

SHARDING

When one replica group
isn't enough.

Sharding partitions the key space so different groups of replicas can be responsible for different subsets of data. Requests can then be routed or proxied to the shard responsible for a particular key.

Partition

Divide responsibility for the key space between multiple shard groups instead of storing every key everywhere.

02

Route

Determine which shard owns a key before processing the corresponding operation.

03

Proxy

If a request reaches the wrong node, it can be forwarded to a replica belonging to the responsible shard.

04

Replicate

Nodes inside each shard continue exchanging state so the partition itself can contain multiple replicas.

THE TRADEOFF

Distribution solves one problem by creating several new ones.

Sharding reduces the amount of data each group is responsible for, but introduces routing, shard membership, synchronization, and consistency concerns across a more complex topology.

WHAT I LEARNED

Distribution changes
everything.

A key-value store is simple when there is one source of truth. Once multiple independent machines own state, even basic operations introduce questions about ordering, synchronization, failures, and consistency.

01

There Is No Global Clock

I learned why timestamps alone are not enough to reason about causality and how vector clocks represent relationships between events across independent nodes.

02

State Gets Complicated Fast

Replication means every node can have a different view of the system at a given moment, making synchronization and metadata part of the core design.

03

Scaling Creates Tradeoffs

Replication and sharding can distribute work and data, but they also introduce routing, communication, consistency, and failure-handling problems.

BIGGEST TAKEAWAY
“The hardest part of distributed systems isn't storing data. It's keeping multiple machines in agreement about what that data means.”

This project gave me practical experience with the problems behind replication, causality, synchronization, and partitioning, while also showing me how quickly complexity grows as a system becomes distributed.
