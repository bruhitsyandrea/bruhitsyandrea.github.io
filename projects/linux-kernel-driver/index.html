Interrupt Handling

IRQ · ISR · request_irq() · tasklets · deferred work

+

What I built

Added interrupt-driven behavior to the PCI driver using request_irq(), with a top-half interrupt handler that acknowledges device events and defers additional processing to a tasklet bottom half.

What I validated

Verified the interrupt path with a 20-trigger rapid-fire stress test with zero dropped events.

What I learned

I learned why expensive processing should not happen in hard-IRQ context and how the top-half/bottom-half model lets a driver acknowledge hardware quickly while safely deferring additional work.

✓ COMPLETED

DMA & Bulk Transfers

dma_alloc_coherent() · DMA buffers · benchmarking · MMIO

+

What I built

Allocated a 1 MB DMA-coherent buffer with dma_alloc_coherent(), verified bulk-transfer contents byte-for-byte, and benchmarked the simulated bulk-transfer path against a naive per-word MMIO readl() loop.

What I measured

The simulated bulk path completed in approximately 19 μs, compared with more than 300 ms for the intentionally naive MMIO baseline.

Engineering constraint

Native EDU DMA could not be exercised on the QEMU ARM virt platform because of the device's 28-bit DMA addressing constraint. I documented the limitation and used a coherent buffer simulation to exercise the Linux DMA allocation API without presenting the result as hardware DMA performance.

What I learned

I learned how Linux provides DMA-safe memory, why DMA addressing capabilities depend on both the device and platform, and how bulk-transfer designs reduce the overhead associated with repeated register-level I/O.

Power Management & Synchronization

D0–D3 · mutexes · ioctl · state machines · concurrency

+

What I built

Implemented a D0–D3 power-state machine with a transition table that permits only valid adjacent state changes. The interface is exposed to userspace through the /dev/edu_pm misc device and ioctl commands.

How I synchronized it

Protected shared power-state transitions with a kernel mutex so concurrent userspace requests cannot modify the state machine simultaneously.

What I validated

Verified that invalid transitions such as D0 → D3 are rejected and stress-tested the state machine with four concurrent threads performing 200 total operations without corrupted device state.

What I learned

I learned how kernel drivers protect shared state under concurrency, when mutex-based synchronization is appropriate, and how explicit state machines enforce safe transitions across userspace requests.

Stress Testing & Reliability

pthreads · concurrency · sustained load · resource safety

+

What I built

Built a multithreaded stress harness that continuously exercised read, write, and ioctl operations across four concurrent threads during a sustained 10-minute test.

What I validated

The driver completed more than 932 million operations with zero kernel warnings or oopses, then unloaded cleanly with no orphaned resources.

What I found

The stress test confirmed kernel-level stability while also exposing a remaining limitation: the internal character-device buffer is not fully synchronized for cross-thread read consistency.

What I learned

I learned how sustained concurrent testing can expose driver correctness and lifecycle issues that sequential tests may miss, and how to distinguish kernel stability from application-level data consistency under concurrent access.
